## 1. Что такое MPI_Comm_split и как создаются группы?

**MPI_Comm_split** — функция для разделения коммуникатора на непересекающиеся подкоммуникаторы (группы).

### Синтаксис:
```c
int MPI_Comm_split(MPI_Comm comm, int color, int key, MPI_Comm *newcomm)
```

### Параметры:
- **comm** — исходный коммуникатор (обычно MPI_COMM_WORLD)
- **color** — идентификатор группы (color). Процессы с одинаковым color попадают в одну группу. `MPI_UNDEFINED` исключает процесс из всех групп.
- **key** — ключ для упорядочивания рангов внутри новой группы. Обычно используют исходный ранг для сохранения порядка.
- **newcomm** — новый коммуникатор для группы.

### Принцип работы:
1. Все процессы вызывают `MPI_Comm_split` с одним и тем же `comm`
2. Процессы группируются по значению `color`
3. Внутри каждой группы ранги назначаются по возрастанию `key`
4. Возвращается `newcomm` — коммуникатор только для данной группы

### Пример (Lab 8):
```python
# color = group_id (0..num_groups-1)
# key = rank (сохраняем порядок)
new_comm = comm.Split(group_id, rank)
```

### В Lab 8:
- Генерируем случайные размеры групп (сумма = size)
- Назначаем каждому рангу `group_id`
- `MPI_Comm_split(group_id, rank)` создаёт `num_groups` независимых коммуникаторов
- Каждая группа работает со своими матрицами изолированно

## 2. Разница между коллективными и парными операциями?

| Характеристика | Парные (Point-to-point) | Коллективные (Collective) |
|----------------|-------------------------|---------------------------|
| **Участники** | 2 процесса (sender, receiver) | Все процессы в коммуникаторе |
| **Примеры** | `MPI_Send`/`MPI_Recv`, `MPI_Isend`/`MPI_Irecv` | `MPI_Bcast`, `MPI_Scatter`, `MPI_Gather`, `MPI_Reduce`, `MPI_Allreduce`, `MPI_Barrier` |
| **Синхронизация** | Неявная (только между парой) | Глобальная (все процессы группы) |
| **Оптимизация** | Ручное управление | Встроенные оптимизации MPI (tree algorithms) |
| **Сложность кода** | Высокая (ручное распределение) | Низкая (один вызов) |
| **Производительность** | Зависит от реализации | Обычно выше (оптимизированные алгоритмы) |

### Примеры в Lab 7/8:

**Парные (Lab 7 blocking):**
```python
# Root раздаёт строки вручную
for i in range(1, size):
    comm.Send(A[displ[i]:displ[i]+count], dest=i)
    
# Root собирает результаты вручную
for i in range(1, size):
    comm.Recv(C_part, source=i)
```

**Коллективные (Lab 8 collective):**
```python
# Один вызов заменяет весь цикл
comm.Scatter([A, MPI.DOUBLE], [A_local, MPI.DOUBLE], root=0)
comm.Gatherv([C_local, MPI.DOUBLE], [C, counts, displs, MPI.DOUBLE], root=0)
```

### Преимущества коллективных:
1. **Алгоритмы дерева** — Bcast/Reduce работают за O(log P) вместо O(P)
2. **Оптимизация под сеть** — MPI реализация знает топологию
3. **Меньше кода** — меньше багов
4. **Синхронизация** — неявный барьер в конце коллективной операции

## 3. Как работают MPI_File_read_at / MPI_File_write_at?

Это функции **MPI-IO** для параллельного доступа к файлам с явным указанием смещения.

### MPI_File_write_at:
```c
int MPI_File_write_at(MPI_File fh, MPI_Offset offset, 
                      const void *buf, int count, 
                      MPI_Datatype datatype, MPI_Status *status)
```

### Параметры:
- **fh** — файловый дескриптор (получен через `MPI_File_Open`)
- **offset** — смещение в байтах от начала файла
- **buf** — буфер с данными
- **count** — количество элементов
- **datatype** — MPI тип данных

### Коллективные аналоги (рекомендуются):
- `MPI_File_write_at_all` — все процессы коллективно записывают
- `MPI_File_read_at_all` — все процессы коллективно читают

### В Lab 8 (Python/mpi4py):
```python
from mpi4py import MPI

# Открытие файла
fh = MPI.File.Open(comm, filename, MPI.MODE_CREATE | MPI.MODE_WRONLY)

# Вычисление смещения для row-distributed матрицы
local_rows, n_cols = matrix.shape
element_size = matrix.dtype.itemsize  # 8 для float64

# Собираем rows_per_proc от всех процессов
rows_per_proc = comm.allgather(local_rows)
displs = np.zeros(size, dtype=int)
displs[1:] = np.cumsum(rows_per_proc)[:-1]

# Смещение в байтах
offset = displs[rank] * n_cols * element_size

# Коллективная запись
fh.Write_at_all(offset, matrix)

fh.Close()
```

### Ключевые моменты:
1. **Смещение в байтах** — не в элементах!
2. **Коллективные версии** (`_all`) эффективнее — MPI может агрегировать I/O
3. **File view** — можно задать сложные паттерны доступа через `MPI_File_Set_view`
4. **Атомарность** — каждая операция атомарна, но порядок между процессами не гарантирован без синхронизации

## 4. Что такое MPI_Wtime и зачем он нужен?

**MPI_Wtime** — функция для измерения времени с высокой точностью (wall-clock time).

### Синтаксис:
```c
double MPI_Wtime(void)
```

### Особенности:
- **Возвращает** время в секундах как `double`
- **Высокая точность** — обычно микросекунды или лучше
- **Синхронизация не требуется** — каждый процесс вызывает независимо
- **Портативность** — работает одинаково на всех платформах MPI
- **Монотонность** — гарантированно не уменьшается

### Использование для замеров:
```python
from mpi4py import MPI

comm = MPI.COMM_WORLD

# Начало замера
start = MPI.Wtime()

# ... вычисления / коммуникация ...

# Конец замера
end = MPI.Wtime()
elapsed = end - start

if comm.Get_rank() == 0:
    print(f"Elapsed: {elapsed:.4f} s")
```

### В Lab 8:
```python
with timer(gcomm, "Group matmul"):
    C_local = A_local @ B

# timer использует MPI.Wtime() внутри
```

### Почему не `time.time()`?
- `time.time()` — системное время, может быть не синхронизировано между узлами
- `MPI_Wtime()` — гарантированно согласовано внутри MPI реализации
- Для распределённых замеров критично использовать `MPI_Wtime()`

## 5. Преимущества коллективных операций над парными?

### 1. **Алгоритмическая эффективность**
- **Bcast**: дерево (binomial tree) — O(log P) шагов вместо O(P)
- **Reduce/Allreduce**: butterfly/reduce-scatter — O(log P) 
- **Scatter/Gather**: оптимизированные паттерны передачи

### 2. **Сетевая эффективность**
- Меньше сообщений суммарного объёма
- Агрегация данных (message combining)
- Оптимизация под топологию (fat-tree, torus, dragonfly)

### 3. **Автоматическая балансировка нагрузки**
- MPI реализация сама решает, как лучше передать данные
- Учитывает гетерогенность узлов/сети

### 4. **Простота и надёжность кода**
```python
# Парные (сложно, ошибки)
for i in range(1, size):
    req = comm.Isend(...)
for i in range(1, size):
    req = comm.Irecv(...)
MPI.Request.Waitall(reqs)

# Коллективные (просто)
comm.Scatter(...)
comm.Gather(...)
```

### 4. **Синхронизация «бесплатно»**
- Коллективные операции неявно синхронизируют участников
- Не нужен отдельный `MPI_Barrier`

### 5. **Совместимость с MPI-IO**
- Коллективные I/O (`Write_at_all`, `Read_at_all`) требуют коллективного вызова
- Позволяют MPI агрегировать запросы к файловой системе

### Количественная оценка (Lab 7/8):
| Операция | Парная (ручная) | Коллективная (MPI) | Ускорение |
|----------|-----------------|-------------------|-----------|
| Bcast    | O(P) сообщений  | O(log P) шагов    | 2-10x     |
| Reduce   | O(P)            | O(log P)          | 2-10x     |
| Scatter  | O(P)            | Оптимизировано    | 1.5-5x    |
| Allgather| O(P²)           | O(P log P)        | 2-20x     |

### Резюме:
> **Коллективные операции — это «стандартная библиотека» распределённых коммуникаций. Они инкапсулируют десятилетия оптимизаций HPC экспертов. Использование парных операций там, где подходят коллективные — это реинжиниринг велосипеда с квадратными колёсами.**
